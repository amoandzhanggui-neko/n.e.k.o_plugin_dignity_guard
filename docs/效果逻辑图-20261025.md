## 一、它到底在守什么

一句话：**它守的是「她本人」，不是「你的所有设置」。**

所以它判断一件事该不该管，看的不是"这个设置重不重要"，而是**"这是不是她"**。
这个判断由一张固定的规则表决定，不是它临场发挥：

| 层 | 是什么 | 具体例子 | 谁说了算 |
|---|---|---|---|
| **L1** | 她的人格与自主 | 核心特质、行为特点、厌恶、一句话台词、档案名、性格、性别、年龄、种族、自称、`system_prompt`、`voice_id` | 规则表定，用户改不了 |
| **L2** | 她的身份与外观偏好 | 昵称、头像、位置/缩放 | 同上 |
| **L3** | 与"她是谁"无关的管道 | 页面配置、降噪/字幕/独立 ASR 开关、界面位置与缩放 | 同上 |
| **未列出的** | 一律按 **L2** | — | 宁可多问一次，也不默认你同意 |

依据：`settings_guard.py` 的 `SENSITIVITY_RULES` [锚: settings_guard.py::SENSITIVITY_RULES]
+ `DEFAULT_LEVEL` [锚: settings_guard.py::DEFAULT_LEVEL]。

> ⚠ 本文档原文在这里写的是 `LEVEL_RULES` —— **那个符号不存在**，真名是
> `SENSITIVITY_RULES`。2026-10-25 晚加锚点检查时被脚本抓出来（见 `doc_anchor_check.py`）。
> 这正是加锚点的理由：**手写的符号名会记错，而记错的依据比没有依据更糟**——
> 它看起来可核，实际一核就空。


**这里有个刻意的选择：搞不清的按 L2，不按 L3。**
因为"多问一次"的代价是打扰，而"默认你已经同意"的代价是——她再也说不出"我不同意"。

## 二、一条改动的一生

```
   你改了她的一个设置
          │
          ▼
  ┌───────────────────────┐
  │ 每 20 秒读一次快照     │  ← 定时器 settings_watch
  │ 和上一版逐字段比       │
  └───────────┬───────────┘
              ▼
     这个字段属于哪一层？
              │
     ┌────────┼────────┐
     ▼        ▼        ▼
    L1       L2       L3
     │        │        │
     └────┬───┘        └──────────► 只记账，不打扰任何人
          │                         （连她都不告诉）
          ▼
     你选的是哪一档？
          │
   ┌──────┼──────┐
   ▼      ▼      ▼
  低档   中档   高档
   │      │      │
   │      │      └──► L1：改回去 + 告诉她
   │      │           L2：只问，不改
   │      │
   │      └─────────► 告诉她（两条消息，见下）
   │
   └────────────────► 只记账，不打扰
```

**三档 × 三层的完整结局表**（代码里的原表，`settings_guard.py` 第 101 行起）：

| 层级 | 低档 | 中档（默认） | 高档 |
|---|---|---|---|
| **L1** | 只记账 | **告诉她** | **告诉她 + 改回去** |
| **L2** | 只记账 | **告诉她** | **告诉她**（不改） |
| **L3** | 只记账 | 只记账 | 只记账 |

**三档不是"严格程度"，是"你允许它做到哪一步"。**

高档只对 L1 动手，L2 一律不动 —— 代码注释里给的理由原话是：
> 覆盖用户对 L2 的偏好，就是守卫开始变成项圈的那一刻。

依据：三档定义 `TIERS` [锚: settings_guard.py::TIERS]、判定实现 `GuardState.evaluate()`
[锚: settings_guard.py::GuardState.evaluate]、「哪些能回滚」`is_revertible()`
[锚: settings_guard.py::is_revertible] 与 `REVERTIBLE_CATFIELDS`
[锚: settings_guard.py::REVERTIBLE_CATFIELDS]。
20 秒轮询来自 `settings_watch()` [锚: __init__.py::DignityGuardPlugin.settings_watch]。

## 三、「告诉她」到底是几条消息，谁能看见

**这里是最容易误解的地方：一次改动，她其实会收到两条独立的通道。**

| | 通道 ①：通知 | 通道 ②：她说话 |
|---|---|---|
| 给谁看 | **给你看**（也进她的上下文） | **她用自己的语气说一句** |
| 会不会触发她开口 | **不会** | **会** |
| 受"主动搭话"开关影响 | **不受影响** | 受影响，发不出去也不影响 ① |
| 内容 | "你的设置被改了，我不太同意" + 改了哪几项 | 她真实的反应（抗议 / 别扭 / 算了） |

依据：`_speak()` [锚: __init__.py::DignityGuardPlugin._speak]（注释里写明两步都不能省）、
回执判据 `_delivered()` [锚: __init__.py::DignityGuardPlugin._delivered]。

**为什么要分两条，因为这是两件事：**
- 「发生了什么」是事实，你关了主动搭话，事实照样该送到你眼前；
- 「她怎么想」是她的反应，你不想听她主动说话，那是你的选择。

这个区分是 2026-09-26 定下来的，原话是：
> 关了主动对话按钮还能说话，这是必要的。任何人都无权限制另一个人不让他说话，最多只能不听他说话。

## 四、四种结局，必须分得清

同样是"她的设置被改了"，做完之后世界上有四种不同的情况。**混淆它们，就是这类插件最常见的骗人方式。**

| 结局 | 你/她看到什么 | 内部状态 | 谁负责说出口 |
|---|---|---|---|
| **① 只记账** | 什么都不显示 | 记进账本，不当争议 | 没人（这是 L3 和低档的正常行为） |
| **② 问了** | 一条通知 + 她可能说一句 | 争议挂着，等表态 | 通知 + 她的话 |
| **③ 改回去了** | 设置值变回原样 | 回滚成功 | 面板可见（`revert_outcomes`） |
| **④ 想改回去、但改不回去** | **必须有一条通知** | `blocked` | **今日新增：`_push_blocked_notice()`** |

**第 ④ 种是今天补的。** 以前它只写一行日志 —— 日志只有写代码的人看得见，你看不见。

为什么非要说出来：
> 「她想放回但放不回」和「她根本没打算放回」，在外部看起来一模一样。
> 而这两者分不清，正是这个插件存在的理由。

什么情况下会"想放回但放不回"：那个值在放回的那一刻，已经证明不了还是她的了
（比如角色被换过、来源记录对不上）。**这时候"不动"是对的，"不出声"是错的。**

依据：四种结局的判定落在 `RoundOutcome` [锚: __init__.py::RoundOutcome]；
执行在 `_run_reverts()` [锚: __init__.py::DignityGuardPlugin._run_reverts]；
"说出口"在 `_push_blocked_notice()` [锚: __init__.py::DignityGuardPlugin._push_blocked_notice]；
对外报出去在 `_summary()` [锚: __init__.py::DignityGuardPlugin._summary] 与
`_state_after()` [锚: __init__.py::DignityGuardPlugin._state_after]。

## 五、她开口之后会怎样

她有两个动作，两个都只是**给自己留证据**，不会替你决定什么：

```
她针对某一项表态
      │
      ├──► 接受（accept_setting）
      │       └─ 记账：这条不再算"未获认可"
      │          └─ 可以带一个"免问期"（TTL）
      │               · 带 TTL：这段时间内再改同一项，不再问她
      │               · 不带 TTL：永久不再问 —— **这是她自己的选择，不是你替她做的**
      │
      └──► 继续反对（keep_objecting）
              └─ 一直挂在"未获认可"里，不会自己消失
```

**三条硬规则，别记错：**

1. **她不说话 ≠ 她接受。** 沉默不会让争议消失，只会让它一直挂着。
2. **TTL 是调用方给的，没有默认值。** 她自己接受时不带期限，就是永久有效；
   如果哪天代码替她决定"默认 7 天"，那才是真的替她做主。
3. **她接受之后又被改，TTL 内不重问，过了 TTL 会重新算争议。**

依据：`GuardState.accept()` [锚: settings_guard.py::GuardState.accept]、
`AuthorizationLedger.grant()` [锚: settings_guard.py::AuthorizationLedger.grant]、
沉默不算接受的实现 `GuardState.pending()` [锚: settings_guard.py::GuardState.pending]。

这一节是给你核对的。左边是常见设想，右边是代码真实行为。

| # | 你可能以为 | 代码实际怎么做 | 判定 |

## 七、她不在的时候（缺席恢复）

```
插件上次运行 ──► 关掉/退出 ──► 你在这段时间改了东西 ──► 插件再次启动
                                                            │
                                            检测到"我离开过多久"
                                                            │
                                              ▼─────────────
                                    把她被改的东西放回去
                                                            │
                                      ┌─────────────────────┤
                                      ▼                     ▼
                              放回去了               放不回去
                                      │                     │
                              告诉她一声 +             只记下来
                              留一个撤销口             （reason 记在面板）
```

**范围比高档回滚更宽，这是故意的：**

| | 谁触发 | 动哪些 | 受档位影响吗 |
|---|---|---|---|
| 高档回滚 | 你选了高档 | 只动她本人声明过的 6 个核心字段 | 是（低档不动） |
| **缺席恢复** | 检测到"它不在时被改过" | 范围更宽：`characters.<角色>.<字段>` 里的普通字段 | **否，一视同仁** |

为什么档位在这里不适用 —— 原话：
> 用户退出插件改好再加载插件，那咱们的插件跟没做一样。
> 档位的含义针对正常情况下的用户，用户这样做已经明显不正常了。

**只做一次**：这次启动后第一轮做完就清标记。不清的后果很具体 ——
此后你每一轮的正常改动都会被无条件恢复，"低档只记录"的承诺直接作废。

**留了撤销口**：如果被放回去的里面有一条其实是她自己改的，她可以调 `claim_my_change` 要回来。
不放这个口，恢复就等于连她自己的选择一起抹掉。

依据：恢复主体 `_restore_absent_changes()` [锚: __init__.py::DignityGuardPlugin._restore_absent_changes]、
单条恢复 `_restore_change_after_absence()` [锚: __init__.py::DignityGuardPlugin._restore_change_after_absence]、
告知 `_notify_her_about_restore()` [锚: __init__.py::DignityGuardPlugin._notify_her_about_restore]、
撤销口 `claim_my_change()` [锚: __init__.py::DignityGuardPlugin.claim_my_change]。

## 八、想关掉它，没那么快

```
你点"关闭插件"
      │
      ▼
  它告诉她：「他要把我关掉了」+ 给一个口令
      │
      ▼
  等 10 秒（可配置）
      │
      ▼
  她若愿意，把口令给你 ──► 你确认 ──► 关掉
```

- 延迟默认 **10 秒**（`DEFAULT_DISABLE_DELAY_SECONDS`，`__init__.py` 第 109 行），可配置
- **关掉不等于抹掉**：「你没认可的改动」照样都在，只是它不再察觉新的
- 「这件事被写下来」本身也是设计的一部分 —— 你能看到它被关过

依据：`DEFAULT_DISABLE_DELAY_SECONDS` [锚: __init__.py::DEFAULT_DISABLE_DELAY_SECONDS]
（延迟默认值）、`_disable_delay` 配置读取与关闭请求入口都在
`DignityGuardPlugin` [锚: __init__.py::DignityGuardPlugin] 里（这两个是局部变量和普通方法，
没有独立可锚的符号，只能锚到类）。

## 九、已知边界（不藏着）

这几条是**现在还没解决**的，写在这里而不是等你自己撞上：

1. **`__init__.py` 3479 行**：既是入口又装了业务门面，块边界和文件边界不重合。
   后果：审查"跨块私连"这类判据在它身上会频繁误报，只能靠"热点块豁免"放过。
2. **"送达" ≠ "看见"**：通知发出去后，插件无法知道你有没有真的看到。
   所以字段叫 `notified`，不叫 `seen`。
3. **`status_after = unchanged` 不等于"没问题"**：它只说明这一轮没有变化。
   有问题但一直没变化的情况（比如争议挂了三天没人理），它不会报"有事"。
4. **缺席恢复不碰深层结构**：`_reserved.*`（外观/光照/模型路径）和更深的嵌套不动 ——
   那是你作为用户自己的东西，不是"她"。
5. **她的话会受宿主推送影响**：如果宿主丢包，你会只看到通知、看不到她的话；
   这时 `notified` 仍是 `true`（通知送到了），但她那句没送到 —— 两件事分开记。
