### 第 3 项是基础设施变更，必须单列说清

**原来的问题（实测，不是推测）：**

| 文件 | 工作区哈希（旧口径） | git blob 哈希 | 一致？ |
|---|---|---|---|
| `__init__.py` | `d2d4c25de33dfc86` | `80f06b9c2372d399` | ❌ |
| `contracts/CT-v2.md` | `192a9f9d3308a19f` | `192a9f9d3308a19f` | ✅ |

根因：`.gitattributes` 是 2026-10-25 才加的，**加之前 checkout 的文件工作区是 CRLF**，
之后写的是 LF。于是**同一个仓库里两种行尾并存**，闸直接读工作区字节算哈希 ⟹
台账里存的是"工作区哈希" ⟹ 换台机器全部对不上 ⟹ 判红 7 把"什么都没改"报成"全改了"。

**修法**：不碰工作区（零风险），改哈希函数为归一化后计算。
**验证（三个来源、三个文件全部一致）：**

```
== 契约哈希三方确认 ==
工作区原始: 7c3abea5a32b9bee
git blob  : 7c3abea5a32b9bee
闸算的    : 7c3abea5a32b9bee
```

⚠ **这条变更让第 1–4 轮台账里的哈希全部作废**（口径不同，不可比）。
本轮 `--stamp` 会把 49 个受控文件的哈希按新口径重建。**跨轮比哈希时，只能比第 5 轮之后的。**

## 三、裁决

1. **本轮通过**（第 5 轮）。四项变更均有可重跑证据。
2. **T1 的完成度要说准**：锚点检查解决的是"图里引用的符号还在不在"，
   **不解决"图说的是不是还对"**。后者仍是人工会审的事 —— 这个边界写在
   `check_doc_anchors()` 的 docstring 和逻辑图第十节里，不许对外说"图和代码已机器对齐"。
3. **哈希口径变更后必须立即 stamp**，否则下一轮所有受控文件都会被判"变了"。
