# 待上交清单 —— 模板

> 用法：复制本文件为 `docs/待上交清单-<日期>.md`，按下面格式填。
> **只装两类事**，其余一律自己改，不要上交（否则清单会变成抱怨信，开发组不会看）。
>
> 依据：skill `neko-plugin-dev` §2.0.5 合规对照 / 完工定义第 10 条。

---

## 一、什么该进这张表

| ✅ 该进 | ❌ 不该进（自己改） |
|---|---|
| 我们用了但宿主 SDK `__all__` 里**没有**的东西 | 拼写错误、命名风格、注释格式 |
| 文档写的和代码实现**不一致**（以代码为准，但要请他们澄清） | 我们自己写错的代码 |
| 文档**没说清**、我们自己做了判断的地方 | 单纯想加功能 |
| 疑似宿主 bug（附复现命令） | 我们没读懂文档 |

**判断口诀**：**改起来只影响我们自己 ⟹ 自己改；改起来要动宿主或要他们拍板 ⟹ 上台。**

---

## 二、表格（每条一行，写满这 6 列）

| # | 位置 | 不符合什么 | 我们为什么这么写 | 建议 | 状态 |
|---|---|---|---|---|---|
| 1 | `__init__.py:32` 导入 `llm_tool`/`tr`/`ui` | 开发指南 §3.1 的导入示例清单里没有这三个名字 | 它们确实存在于 `plugin/sdk/plugin/__init__.py` 的 `__all__`（第 101/103/109 行），且插件已稳定使用 | 请把这三个补进 §3.1 的示例清单，或明确"§3.1 不是穷尽清单" | 待回话 |
| 2 |  |  |  |  |  |
| 3 |  |  |  |  |  |

**列含义（别省列，省了对方就得反问）：**
- **位置**：`文件:行号`，能点进去的
- **不符合什么**：引文档章节号 / 引代码行号，二选一必须给
- **我们为什么这么写**：给出依据（代码事实优先于文档），不要写"我觉得"
- **建议**：给对方一个可执行的动作（补文档 / 补导出 / 澄清 / 允许例外）
- **状态**：待回话 / 已同意 / 已否决 / 已降级 / 已删

## 三、处置记录（开发组回话后填，一条不能漏）

| # | 他们的回复 | 处置 | 做了什么 | 完工定义第 10 条是否仍 √ |
|---|---|---|---|---|
| 1 |  | 保留 / 换写法 / 降级 / 删除 |  |  |

**处置判据（来自 skill §2.0.5，不许拍脑袋）：**

| 性质 | 处置 | 额外要求 |
|---|---|---|
| 硬红线（写别人数据 / 越权 / 未导出 API） | **删** | 不商量 |
| 能力受限（他们不允许这个能力） | **降级** | **必须写清降级后少了什么功能**，让掌柜知道代价 |
| 只是写法不合 | **换写法** | 保留原功能 |
| 他们同意 | **保留** | 把这条写进 skill §8 已知边界，下次别再问一遍 |

---

## 四、提交方式

- **一次性给，不零散问**：攒到交付时一起发
- **一页为限**：超过 10 条说明我们自己没把关，回去先自己筛
- 附**复现命令**：让他们能自己跑一遍看到问题，而不是听我们描述

---

## 五、自查清单（发出去之前先过一遍）

- [ ] 每条都有 `文件:行号` 或 `文档章节号`
- [ ] 每条都有"我们为什么这么写"的依据（代码事实 > 文档）
- [ ] 每条都有可执行建议（不是"请指教"）
- [ ] 总数 ≤10 条
- [ ] 没有一条是"我们没读懂就当成他们错"
- [ ] 附了复现命令
