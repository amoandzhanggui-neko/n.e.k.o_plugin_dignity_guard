## 二、三家意见

### 红队（找最危险的）

1. **最危险：判红 10 条只实现 5 条，但 skill 写的是「完工定义十条」。** 容易让人误以为全套都上了。**必须在本裁决表和 skill 里都写明"实现到第 5 条"**，不许含糊。
2. **`assembly_check.py` 验不到真启动**（`NekoPluginBase.__init__(self, ctx)` 要宿主注入的 ctx）。它输出"装配检查通过"这四个字，很容易被读成"插件能跑"。**必须在输出里固定打印边界声明**（已做，但要在裁决表留痕）。
3. **接缝快照只覆盖契约层**，不覆盖运行时实际字段。判红 2 的后半（"实测 ∉ 允许态 ⟹ 红"）**没有实测态来源**，现在只能判"声明变了"，判不了"实际不符"。
4. **`__init__.py` 3266 行**使 B6 与其它块文件级耦合，§4-R2（接缝私约）会频繁误报。

### 工程落地（可行性与成本）

1. 全链跑一次：测试 208s + 装配 8s + 快照 1s + 块校验 <1s ≈ **3.7 分钟**，可接受。
2. **但 `state.sh` 默认跑装配（8s）会让状态板从"几秒"变"十秒级"** —— 已改头部说明，不是隐藏成本。
3. **脆弱点：契约解析依赖固定 markdown 表格格式**。格式一改就解析不出字段，且**会静默返回 0 字段**（我加了一层"字段数为 0 就报错"？→ 见待办 T2）。
4. `block_check.py` 的表格解析同样脆弱，但它是**声明性文件**，格式稳定，风险低于契约表。
